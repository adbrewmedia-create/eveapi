Working with Viktor and Eve

A practical guide for AdOps, Commercial and Content teams on what you can ask Viktor to do in Slack, what Viktor needs from you, and what happens in Eve afterwards.

Based on the Eve API live docs (specification v1.0.0) and the existing Eve API pages in Confluence. Last compiled 15 October 2026. The Slack wording in the examples is illustrative; the fields, rules and outcomes come from the API.

1. What this is

Eve is GDC's AdTech system of record: brands, offers, operator deals, destination URLs, program accounts and the site placements that connect them. Viktor is the Slack assistant that works with Eve on your behalf. You describe what you want in plain language using names (brand, site, country); Viktor finds the matching records, collects what's missing, and either saves the work for review or performs the change.

Everything Viktor does goes through the Eve API, so anything Viktor can do is also attributed to you in Eve's audit trail, using your Slack email.

Where to ask

Workflow requests go in #adops-workflow-agent, database sync requests in #ask-adtech, and API create/read/update/delete requests in #adtech. Full details in section 11.

Four kinds of request

Rule of thumb

If a change touches live offers, deals or destination URLs, use a workflow so someone reviews it. Direct edits skip review. This is a recommendation, not an enforced rule; the API allows both.

2. How a request flows

  1. You ask in SlackUse names, not IDs. "10Bet", "gambling.com", "United Kingdom", "Casino".
  2. Viktor resolves names to Eve recordsIt searches Eve for each name. If a name matches several records (for example "10Bet" and "10Bet AU"), Viktor asks which one you mean. Each search shows at most 10 results, so a very broad name needs narrowing.
  3. Viktor asks for what's missingEach workflow has required inputs (see section 3). Viktor will not guess certain choices such as publish status or default flags; it asks every time.
  4. Viktor checks and confirmsFor offers, it can run a non-blocking currency check against the GEO and show you a warning before anything is saved.
  5. You choose: draft or send to QASee the table below.
  6. Review and approval in EveA person checks the workflow in Eve and approves it. Only then are the changes applied.

Draft or send to QA

Draft (default)Send to QA
Saved in Eve AdOps queueYes, status draftYes, status pending_qa
Jira ticketNo. A person still has to send it to Jira from the Eve UI.Created immediately. Viktor gives you the ticket key.

Which Jira board

Every workflow goes to either the US Commercial or the ROW Commercial board. Viktor asks which. The ticket prefix you get back depends on the workflow and board.

Currently draft only

Bulk feature update and bulk feature removal cannot be sent to QA yet, because their Jira issue type isn't configured. Viktor must use draft for these.

Who Viktor thinks you are

Viktor identifies you by your Slack email and never asks you for it. That email must belong to an Eve user. If it doesn't, every write fails with "No user found with the provided email." Ask the AdTech team to create or fix your Eve user.

Offer create

Creates a new offer for an existing brand, plus its site offers, destination URLs (SDURLs) and operator deals, across every combination of site, product, country and language you select.

Use it when
A brand is already in Eve and you're launching a new bonus or promotion.
Have ready
  • Brand, product types, sites, countries (and regions where a country has them)
  • Offer type, offer currency, start date, optional end date
  • Offer description and terms and conditions
  • Destination URL(s), or the existing SDURL(s) to reuse
  • Deal terms (see the table above) or the existing deal(s) to reuse
Viktor always asks
  • Traffic source: one source or several. Several sources create one offer per source, and each source needs its own destination URLs.
  • Offer currency, even if it seems obvious. Viktor checks it against each country's expected currency and warns if it differs, or if the description contains a different currency symbol.
  • Default site offer? Whether these site offers become the default for their site, country and region.
  • Publish? Whether the offer and its parent records go live once approved.
  • Default URL? For each destination URL. At most one per submission can be the default.
  • Language, for every site and country pair that has languages. You can't skip it.
Choices you make
  • URLs: create new, or reuse existing. Scope: one generic URL set, or per region.
  • Deals: create new or reuse existing. Scope: same for all, per site-brand-product, or per site-brand-product and region.
  • Limit the combinations: if you don't want the full cross-join of sites, products, countries and languages, tell Viktor which to include.
Description text
By default HTML is stripped and any site-specific description automation is applied. Say so if you need your HTML kept exactly as written.
Result
A workflow titled like "Offer Create > 10Bet > gambling.com", with a link to it in Eve and, if sent to QA, a Jira key.

Offer edit

Changes existing offers, their destination URLs and their operator deals. You only supply what changes; everything else stays as it is.

Use it when
Bonus terms, dates, URLs or deal rates change on live offers.
How Viktor finds offers
By name, optionally narrowed by brand, site, country, region, or "only offers that have a default site offer". Viktor then lists the site offers under each offer so you can target specific ones.
You can change
  • Offer type, currency, start and end date, description, terms and conditions, default flag
  • Destination URLs: add new ones, or edit existing ones per site offer
  • Operator deals: add new ones, or edit existing ones per site offer
Heads-up
  • Publish is one-way. You can publish through an edit, but never unpublish. To take something offline, use Brand removal.
  • When editing an existing deal, send only the changed numbers. The start date is optional and keeps its current value if omitted.
  • Currency changes get the same GEO mismatch warning as offer create.

Brand import

Creates a new brand from the operator's onboarding form (CSV or Excel), and registers it on the sites and countries you choose. Optionally creates its first offer at the same time.

Use it when
You have the operator's completed onboarding form. No form? Use Brand end-to-end.
Have ready
  • The file, with two columns named Question and Responses. CSV, XLSX and XLS are accepted.
  • Affiliate program, sites, countries, regions (if any country has them), languages
One file at a time
Each submission takes one file. For several brands, Viktor submits one workflow per file.
Constraints
  • Each site and country pair must already exist in Eve as a site country version.
  • You can't mix countries that have regions with countries that don't. Split them into two imports.
  • Regions are required when any selected country has regions, and they must belong to the selected countries.
  • Languages are required whenever the site and country pair has any.
Optional offer
Viktor asks every time whether to create an offer. If yes, it needs offer type, currency, start date, description, new destination URLs and new deals. Reusing existing URLs or deals isn't available here.
If the file fails
Viktor relays the parse error, for example "Row 3: missing required column 'Responses'". Fix the file and resubmit.

Brand end-to-end

Sets up a brand from scratch without a form: the brand, its products, site placements, offer, site offers, destination URLs and operator deals in one workflow.

Have ready
  • Brand name, which must be unique across all existing brands. A duplicate is rejected. Optional established year.
  • Affiliate program, products, sites, countries, regions and languages
  • Offer details, URLs and deal terms
One product or several
With one product, Viktor collects a single offer. With two or more, it collects a separate offer for each product (type, currency, dates, description, terms, default flag).
Always new
URLs are always created new and deals always created new. Every URL and deal entry carries a language.

Removes a brand from selected site, country and product placements, either by hiding it or by deleting the placements.

Have ready
The brand, the placements to act on (each is one site, country and product combination for that brand), optional product-type filter, and a reason. The reason goes into the Jira ticket.
Soft or full

Program account migration

Moves all operator deals from one or more source program accounts to a single target program account, and marks each source as Migrated.

Have ready
Source account(s), the target account, and a comment explaining why. The comment appears in the Jira ticket and is stored permanently with the migration record.
Rules
  • The target can't also be a source.
  • Accounts already marked Migrated can't be a source or a target. They don't appear in search.
Heads-up
Approval moves every deal on the source accounts. Check the source list carefully before sending to QA.

Inactivate program account

Requests that one or more program accounts be set to Inactive.

Have ready
The accounts, and one shared reason. The reason goes into the Jira ticket, the Revenue Accounting Slack notification and each account's status log.
Approval-gated
Submitting does not change any account. A Revenue Accounting approver must confirm the request in Eve first.
Rules
Already-inactive accounts don't appear in search and can't be selected.

Bulk feature update

Adds features to many records at once. It has two independent sections, and you can use one or both in the same request.

Brand section
Attach one or more payment providers or licence jurisdictions to one or more brands. For payment providers you can also set country, regions, language, and whether deposits and withdrawals are allowed. These extra fields are only valid for payment providers.
Brand product section
Attach one or more product features (for example a software provider) to one or more brand products.
Rules
  • Regions require a country, and every region must belong to it.
  • One country and one language apply to every payment provider in the request. For different countries, make separate requests.
  • Every feature key must match the chosen type. Attaching a licence where a payment provider was selected is rejected.
  • Duplicate IDs in a list are rejected.
On approval
Best effort per record: something already attached is skipped, not treated as an error.
Status
Draft only for now

Bulk feature removal

The reverse of bulk feature update, but it handles one scope per request.

Choose one scope
  • Licence jurisdiction: remove licences from brands.
  • Product feature: remove features from brand products.
Sending fields for both scopes is rejected. Payment providers aren't covered by this workflow.
On approval
Best effort per pair. If a brand doesn't have that licence, or a product doesn't have that feature, it is skipped.
Status
Draft only for now

4. Looking things up

You can ask Viktor to find records any time. These are read-only and take effect on nothing.

Quick lookups

These return a name and ID, up to 10 matches. If there are more, Viktor tells you the total so you can narrow the search.

You can findTips
Brands, brand products, sites, product types, offer types, offers, affiliate programs, program accounts, operator deals, countries, currencies, offer sourcesPartial names work.
LanguagesGive a site and country together to see only languages valid for that combination.
Country regionsSearch by two-letter code (for example AL). Searching by full name needs the country as well. Results show the code, not the full name.
Site country versionsLabels look like "Gambling.com > English > United Kingdom" and are hard to guess. Filter by site and country instead of typing a label.
Site brand productsFilter by site, country, brand, product type or region instead of typing a label.
Site offersGive the offer to list every published site offer under it.

Browsing records in detail

For fuller records, Viktor can list any of the Eve resources below. Results are paged (15 by default, up to 100), can be sorted, and can be filtered. Examples: offers for a brand product, brands by affiliate program, brand features for a brand and country, operator deals by program account. The full list of filters for each resource is in the Eve API docs.

Deleted records still show up

Opening a record by ID returns it even if it was soft-deleted, with a deleted date shown. Listing can include or exclude deleted records on request.

5. Direct edits

Besides workflows, Viktor can create, update and delete individual records. These happen immediately and appear in Eve's audit trail under your name.

No review step

Direct edits have no draft, no QA and no approval. Check the record IDs and values before you tell Viktor to go ahead.

The exact fields each resource accepts are listed in the Eve API docs under Resources.

What you can do

  • Create or update any writable resource. Send only the fields you're changing when updating.
  • Delete means soft delete: the record is marked deleted, never erased. This API has no restore, so recovery needs the AdTech team.
  • Bulk update offers: apply one change (for example a new expiry date) to many offers at once, in a single all-or-nothing operation.
  • Attach or detach related records:
    • Product features on brand products
    • Licence jurisdictions on brands, for one brand or many at once. A bulk attach is all-or-nothing: if one brand rejects it, none are changed.
  • Brand payment providers are managed as brand features (type "Localised Payment Provider") for a specific country, not as a relation on the brand. Viktor first checks whether the brand already has that provider for that country before adding it.

What Viktor typically checks first

  • The exact record, by ID, so you are not changing a similarly named one
  • For attributes, the valid attribute types
  • For attaching features, that the feature's type matches the relation (a licence can't be attached as a payment provider)

6. Brand data for content

Separately from AdOps requests, Viktor reads live commercial data from Eve before generating brand reviews, so that Eve is the source of truth for bonus amounts, payment methods and licences.

DataWhat it contains
Brand detailName, website, colour, logo, established year, owner, address, support contact
LicencesLicensing jurisdictions and the country for each. Empty list if none on record.
Payment methodsGlobal and country/state-specific methods, deposit and withdrawal support, times, limits and fees. Filterable by country and region.
Product attributesAttributes for a brand product, filterable by country and region
OffersWelcome offer details: type, description, size, percent, free spins, wagering, minimum deposit, promo code, expiry, terms, call-to-action link
RegionsWhich states or regions a product is mapped to, and whether each is published
USPsSelling points, resolved from the most specific scope: region first, then country, then general
Destination URLsTracking links in all variants (desktop, mobile, PPC, deeplinks)
Regional placementsAll regional placements for a site country version, including unpublished
Things to know
  • Publish status is not filtered. Records come back whether live or not, so Viktor checks publish and expiry fields before using them.
  • Links keep their {{tracker}} placeholder. It's filled in by the site at display time.
  • If Eve data looks wrong, the fix belongs in Eve (ask AdOps), not in the content.
  • Eve covers commercial data only. Editorial content, awards and video aren't in Eve.

7. Rules Viktor applies

  • Viktor never guesses publish status, default site offer, default URL, the traffic source count, or the offer currency. It asks every time.
  • Offer currency is not deal currency. One is shown to players, the other is how commission is paid.
  • Currency warnings don't block. The workflow still saves; the warning is there so you can correct before sending to QA.
  • Languages are mandatory where a site and country pair has any, even if you already said "English". Viktor resolves the ID.
  • Regions are all-or-nothing per request: don't mix countries with and without regions.
  • Edits can't unpublish. Only removal workflows take things offline.
  • Nothing is hard-deleted. All deletes are soft deletes.
  • Everything is attributed to you. Your Slack email is recorded as the actor.

10. Known limits

  • Bulk feature update and removal can only be saved as drafts for now.
  • Offer edit cannot unpublish.
  • No API restore for soft-deleted records.
  • Brand import takes one file per request.
  • Bulk feature removal doesn't cover payment providers.
  • Payment-provider country and language apply once per bulk feature update request.
  • Production base URL and support contact: ask the AdTech team. The API reference is at eve.gdcgroup.tech/api-docs.
